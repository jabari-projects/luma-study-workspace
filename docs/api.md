# API reference

The FastAPI application is served from the URL configured as `VITE_API_BASE_URL` in the frontend. Except where noted, protected endpoints require `Authorization: Bearer <JWT>`. FastAPI also exposes its generated OpenAPI documentation when the service is running.

## Service and authentication

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/health` | **Liveness only:** the server process is running. It does **not** check the database, so a 200 here is not proof that accounts, notes or search work. |
| GET | `/health/ready` | **Database readiness:** runs a tiny read-only query (no rows) with a 5-second limit. Returns 200 `{status: "ready"}` only if the database answers; otherwise 503 with `database` set to `not_configured`, `unreachable` or `timeout`. No error details are returned. |
| POST | `/signup` | Starts a signup and returns **202** `{"status":"check_email","email","ticket","resend_after_seconds":60,"code_expires_in_seconds":600}`. **No account is created yet**: the username and the argon2id password hash wait in a pending row until the emailed code is entered. `ticket` is random, kept only by the browser (session storage), and is needed with the code. The answer and its timing (padded to 0.8 s) are the same whether or not the email has an account. An existing owner gets a short "someone tried to sign up" notice (at most 1 per hour). For an existing email a decoy pending row is saved that can never succeed and whose code is never sent, so wrong tries lock and expire the same way and code checks reveal nothing either. Errors: 400 `password_invalid` (8–128 characters), 400 `username_taken` (checked against real accounts only, the same for any email), 429 `rate_limited` (10 signups per IP per hour). |
| POST | `/auth/verify-email` | Pending signup: body `{email, ticket, code}`; creates the account (verified) and returns a session. Logged-in account (Bearer token, no ticket): body `{code}`; marks the current address verified. Codes are bound to the address they were sent to, so a code can't verify a different email after a change. Errors (400): `code_incorrect` (also for unknown emails, wrong tickets, or no ticket and no login), `code_expired` (after 10 minutes), `code_locked` (after 5 wrong tries on one code), `account_exists` (someone with the inbox finished another signup first), `username_taken`. 429 `rate_limited`: 30 tries per IP and 10 per email or account per 10 minutes. Pasted codes with spaces or dashes work. |
| POST | `/auth/resend-code` | Body `{email, ticket}`. Always **202** `{"status":"sent_if_possible","resend_after_seconds":60}`. Sends a new code only for this browser's pending signup, within the limits: 60 s between codes, 5 per hour and 10 per day per signup, 20 per hour and 50 per day per inbox across all signups (looser, so strangers can't easily use up the owner's allowance), 20 requests per IP per hour. **A new code retires older unused codes for that signup.** |
| POST | `/login` | Returns a session with `user.email_verified`. Older unverified accounts can log in (the email is matched without regard to capital letters), but AI tools answer 403 `email_unverified` until they enter a code; the code page sends one automatically. Older plaintext passwords are upgraded to a hash on the next successful login. Failure: 401 "That email or password is wrong." After 10 failed tries for the same email and IP in 15 minutes, it returns 429. |
| POST | `/auth/send-verification` | Logged in: sends a new code. 429 `resend_cooldown` (with `retry_after`) inside the 60 s cooldown, 429 `rate_limited` at the account's or the inbox's hourly/daily cap, 503 `email_send_failed` when the email provider refuses. |
| POST | `/auth/request-reset` | Emails a reset link to `{frontend}/reset-password?token=…`. It always returns the same message and takes about the same time, whether or not the account exists. Requests are rate-limited. Only a SHA-256 digest of the token is stored, and tokens are never logged. Links work for 30 minutes; a newer link replaces the older one. |
| POST | `/auth/reset` | Resets a password with a valid reset token (8–128 characters). The token is used up in the same conditional update that sets the password, so a link works once even with parallel requests; replays get 400 `reset_invalid`. Older sessions stop working: their next request gets 401 "Session expired. Please log in again." Using the emailed link also marks the email verified. |

Error bodies for the account routes: `{"detail": "<friendly message>", "error_code": "<code>"}` plus `retry_after` (seconds) on 429.

**Current password checks** (`PUT /me/email`, `DELETE /me/account`) share one limit per account: 5 tries per 15 minutes (a right password clears it) and 10 per day (a right password does not). So every `PUT /me/email` that reaches the password check uses one of the 10 daily tries, right or wrong; `POST /me/email/resend` uses none. The 429 `rate_limited` carries `retry_after` (900 for the 15-minute limit, 86400 for the daily one).

**Codes:** 6 digits, stored only as an HMAC-SHA256 digest keyed with the server secret and bound to the user and purpose. Never logged.

**Free AI allowance:** AI routes need a verified email (403 `email_unverified`). The daily free count is kept per user *and* per normalized email (lowercase, `+tag` removed, Gmail dots removed) under a keyed hash, so deleting and re-creating an account doesn't reset it. Free users run one AI request at a time per email on a server (429 "One AI task at a time"). This lock is per process: Render runs one `uvicorn` process today; with more workers or instances the reservation would have to move into the database. This doesn't stop one person from using many different email addresses.

## Shared study sets and analytics

Shared study sets are for signed-in students only. Both search routes need a bearer token (401 without one). Results show the owner's username and nothing else about them: no user id, display name, photo or counts. Every API response carries `X-Robots-Tag: noindex, nofollow`, and `GET /robots.txt` disallows everything.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/public/topics?query=` | Signed in. Searches shared notes, flashcards, and summaries by their title, content or tags (never by a stored or old name), newest first, up to 80. Each item: `id, study_type, title, preview, tags, username, published_at, created_at`. `preview` is plain text with Markdown marks removed. `username` is the owner's current username, or `student` if it is unknown. |
| GET | `/public/users?query=` | Signed in. Finds students who shared something, by username only (3+ letters; shorter queries return `[]`). Each result: `username, items`. Looks the username up first, so a student who shared long ago is still found. Usernames are letters, numbers and `_`, so any other character returns `[]`. Up to 40 people, each with their newest 24 items. Closest name first, then A to Z. |
| GET | `/robots.txt` | `Disallow: /` for every crawler. |
| POST | `/analytics/events` | Accepts an authenticated batch of analytics events. |

## Profile, notifications, and realtime

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET / PUT | `/me/profile` | Read or update the current user's profile fields. |
| POST / DELETE | `/me/avatar` | Upload or remove a JPEG, PNG, or WebP avatar. |
| POST / DELETE | `/me/theme-image` | Upload or remove a JPEG, PNG, or WebP custom theme image. |
| PUT | `/me/username` | Change the current username. |
| PUT | `/me/email` | Step 1 of an email change. Body `{new_email, current_password}`. Answers **202** `{"status":"code_sent_if_possible","resend_after_seconds":60,"code_expires_in_seconds":600}` and emails a 6-digit code to the **new** address; nothing changes yet. The answer is the same whether or not the new address already has an account: then a code is saved but never sent (and does not count toward that inbox's caps), so the route can't be used to look up emails or to use up someone's inbox. Codes are limited per account (60 s between codes, 5 per hour, 10 per day, shared with `/auth/send-verification`); those limits are checked **before** the password, so they don't use a password try: 429 `resend_cooldown` or 429 `rate_limited`, both with `retry_after`. The only silent case: when the new inbox is at its own cap (20 per hour, 50 per day across all accounts and signups) the answer is still 202 but no code is saved or sent, since saying so could hint who uses the address. Calling it again for another address replaces the old code. Errors: 400 `wrong_password`, 400 `password_needed` (the account has no password yet: use Forgot password first), 400 `same_email`, 403 `admin_email_locked`, 429 `rate_limited` (password limit, see above), 503 `email_send_failed` (the code could not be saved), 422 when `current_password` is missing. |
| POST | `/me/email/resend` | A new code for the email change already started, without the password again. Body `{new_email}`: must be the address of the account's newest code, while that code is unused (used, replaced by another start, or the current address: 400 `no_pending_change`, so start again with `PUT /me/email`). Same 202 body, same answer for taken addresses, same per-account limits (429 `resend_cooldown` / `rate_limited` with `retry_after`) and the same silent inbox cap. The new code replaces the old one. |
| POST | `/me/email/confirm` | Step 2. Body `{new_email, code}`. Returns the updated profile; the new address counts as verified (the code proves the inbox), and the old address gets a "your email was changed" notice. Errors (400): `code_incorrect` (also when no code was sent, or for the current address), `code_expired`, `code_locked`, `email_taken` (another account took the address before the code was typed), `email_change_failed` (saving failed, for example a signup took the address at the same moment). After `email_taken` and `email_change_failed` the code is used up: start again with `PUT /me/email`. 429 `rate_limited` (`retry_after` 600): 10 tries per account per 10 minutes, shared with the signed-in `POST /auth/verify-email`. |
| DELETE | `/me/account` | Delete the current account and related application data. Needs a JSON body `{current_password}`, so a stolen sign-in alone can't delete the account. Errors: 400 `wrong_password`, 400 `password_needed`, 429 `rate_limited`, 422 when the body is missing. 500 means the deletion is incomplete and safe to retry. |
| GET | `/notifications` | List the current user's notifications. |
| POST | `/notifications/read` | Mark submitted notification IDs as read. |
| WS | `/ws` | Authenticated WebSocket connection. Send the token as `Authorization: Bearer <token>`, or (browsers can't set headers on a WebSocket) as the subprotocol pair `Sec-WebSocket-Protocol: bearer, <token>`; the server answers with the `bearer` subprotocol. A token in the URL is refused, because hosting logs keep URLs. |

## AI, transcription, and subscription endpoints

| Method | Endpoint | Purpose |
| --- | --- | --- |
| POST | `/api/generate-notes` | Turns a picture into study notes. Body: `{image}`, a base64 data URL (PNG, JPEG, WEBP or GIF). Returns the same `{title, summary, notes, key_terms, flashcards: [{front, back}], truncated}` shape as `/api/notes-from-text` (`truncated` is always false). Uses 1 notes turn, counted only when the notes come back. A picture that isn't PNG/JPEG/WEBP/GIF answers 400, and a body over 21 MB (about a 15 MB picture) answers 413; both happen before any turn or rate-limit slot is used. The AI answer may use up to 2,500 output tokens (it was 700 before). **The picture is sent to OpenAI**; Luma doesn't store it. Other errors: 401, 403 (free daily limit), 429 (too many requests), 503 (AI not configured or not working). Requires authentication and OpenAI. |
| POST | `/api/transcribe` | Transcribes a multipart `audio` upload (WAV, MP3, M4A/MP4, WEBM, OGG; up to 25 MB) and returns `{transcript}`. Uses OpenAI speech-to-text (`OPENAI_TRANSCRIBE_MODEL`, default `gpt-4o-mini-transcribe`) when `OPENAI_API_KEY` is set, otherwise Deepgram. **The audio is sent to that provider**; Luma doesn't store it. The 25 MB cap is enforced on the bytes actually received, not only the `Content-Length` header (413). Other errors: 400 (empty or unsupported audio), 401, 403 (free daily limit), 429 (too many requests), 503 (no provider configured). Requires authentication. |
| POST | `/api/notes-from-text` | Turns text (a transcript, pasted words, an extracted file or web page) into study notes. Body: `{text, source_kind: audio\|paste\|file\|link\|youtube, source_label?}`. Returns `{title, summary, notes, key_terms, flashcards: [{front, back}], truncated}`. Text over 60,000 characters is cut and `truncated` is true. Counts toward the free daily notes limit. Requires authentication and OpenAI. |
| POST | `/api/summarize` | Makes a short summary of a note. Body: `{text}` (at least 20 characters; text over 60,000 characters is cut). Returns exactly `{title, summary}`; `summary` is a few plain sentences. It does not save anything: the page saves the summary with `POST /summaries`. Uses 1 notes turn (the same free daily notes limit and the same per-minute limit as the other notes tools), counted only when the summary comes back. The AI answer may use up to 800 output tokens. **The note's text is sent to OpenAI.** Errors: 400 (too few words), 401, 403 (email not checked, or free daily limit), 429 (too many requests, or another AI task is running), 500 (the AI answer was unusable; no turn used), 503 (AI not configured or not working). Requires authentication and OpenAI. |
| POST | `/api/import/link` | Reads the main text of a public web page. Body: `{url}`. Returns `{title, text, site_name, url, truncated}`. Private, local and cloud-metadata addresses are refused, redirects are re-checked, and pages over 3 MB are dropped (each connection times out after 10 seconds, with a 20-second deadline for the whole fetch). YouTube links return 422 with `code: "youtube"` (students paste the transcript instead, because YouTube blocks cloud servers). Errors use `{error, code}` with codes `blocked`, `fetch`, `pdf`, `type`, `too_short`. Requires authentication; does not use AI. |
| POST | `/api/create-checkout-session` | Creates an authenticated Stripe Checkout subscription session, reusing the account's linked Stripe customer when there is one. Answers 409 for a Premium account with no billing link (a legacy subscription): a new checkout would hide the unlinked subscription from status refresh and account deletion, so the account must be linked by hand first. |
| POST | `/api/stripe-webhook` | Verifies Stripe's webhook signature. `checkout.session.completed` is re-read from Stripe and links the customer/subscription ids to the account in `billing_accounts` / `billing_subscriptions` (refused if the owner fields disagree or the customer belongs to another account). `customer.subscription.*` events apply only to already-linked subscriptions; ownership is never guessed from email. Answers 500 on database or Stripe errors so Stripe retries. |

The AI routes enforce rate limits and the free daily limit. The daily limit **fails closed**: if usage can't be counted (for example, the database is down), free users are told they've reached the limit instead of getting unlimited AI. Every OpenAI and Deepgram call has a true total deadline (100 seconds for notes and images, 150 for transcription; see `backend/app/deadline.py`), below the browser's wait (120 and 180 seconds). Calls aren't retried automatically, and a call that misses its deadline answers 503 without using a free turn. OpenAI Responses calls send `store=false`, and Deepgram calls send `mip_opt_out=true`. Text sent to `/api/notes-from-text` or `/api/summarize` goes to OpenAI, plus the page's title or link for web and YouTube imports. Students' own file names are not sent: audio goes as `recording.<ext>`, and uploaded documents are labeled "Uploaded file". `/api/transcribe` also returns 403 when a free student has no notes turns left, so a talk-to-text turn isn't wasted. Service keys must stay server-side. `TRUSTED_PROXY_HOPS` tells the server how many proxy hops to skip in `X-Forwarded-For`. Leave it at `0` (ignore the header; per-email limits still work) until it's checked on the real host. On Render, Cloudflare sits in front of Render's proxy, so `1` would probably pick a Cloudflare address, not the visitor's. Check it on staging before changing it.

## Monthly feedback poll

"If it ain't broke why fix it?!": a monthly yes/no poll about what Luma should change. **Not live yet**: the tables come from `backend/app/schemas/migrations/2026_11_18_monthly_feedback.sql`, which is not applied. Until it is, student reads return empty data and writes answer 503 `feedback_unavailable`. It is the first file of this release, run before `2026_11_19_maintenance_state.sql` and `2026_11_19_student_work_versions.sql` (name order; see `docs/deployment-checklist.md`).

- **Maintenance breaks:** ballots, skips and every admin change are ordinary writes for the break (`backend/app/maintenance.py`): allowed until the grace time ends, then refused with 503 `maintenance_draining`, and 503 `maintenance_active` during the break. Reads that also tidy up (`GET /admin/feedback/polls` making the next drafts, the voter-key cleanup) skip that writing whenever writes are refused, so a read never writes during a break.

- **Schedule:** a poll opens on the last Sunday of its month at 12:00 noon America/Chicago and closes the next Sunday at noon. Status comes from the clock: `[opens_at, closes_at)`. Only an admin-approved poll ever opens; drafts are never published by themselves.
- **Votes:** signed in and email verified. One ballot per account and per email (a keyed hash of the normalized email) per poll, enforced by the database. A retry is answered `200 already_received` and never counted twice. Voting gives no rewards. One-vote-per-email uses the address at voting time: the email key is stored with the ballot and never recomputed, so changing an account's email while a poll is open doesn't move the key. The old address stays used up for that poll (whoever verifies it next sees "already answered"), and the new address isn't marked as having voted.
- **Privacy:** students see results as percentages only, after the poll closes, for the last 24 closed polls, and only for questions at least 5 students answered. Admins see comment text, never who wrote it (no user id, email or username in any response). While a poll is open, admins see only how many students answered; per-question counts, comments and themes appear after it closes, so nobody can match a known student to their answers by watching the numbers change.
- **Email key:** the per-email hash is keyed with a value derived from `JWT_SECRET_KEY` and a fixed label (`HMAC(JWT_SECRET_KEY, "luma-feedback-voter-key-v1")`), so it never doubles as a token signature. Rotating `JWT_SECRET_KEY` signs everyone out and resets every email key, so rotate it only between polls: rotating while a poll is open lets a deleted-and-remade account vote again in that poll. After a poll closes, a deleted account's key is cleared, so its answers can't be traced back to the email.
- **Errors** use `{detail, error_code}`. Times are UTC ISO strings ending in `Z`; admin `*_local` fields are Chicago wall-clock `YYYY-MM-DDTHH:MM`.

Admin writes are limited to 300 an hour per admin (429 `rate_limited`). Any non-admin gets 403, and no token gets 401. Deleting an account keeps that student's poll answers in the totals without their name and deletes their poll comments and skip records. Ballots can only be written by the database function `feedback_submit`; the service role has no direct insert on ballots or answers.
